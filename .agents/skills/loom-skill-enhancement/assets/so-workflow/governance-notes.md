# Loom Skill Enhancement Self-Bootstrap Governance Notes

- Bound SO package runtime version: `0.4.10`.
- This skill is self-bootstrapped through a checked-in workflow template under Loom Skill Orchestrator governance.
- This self-bootstrap pass uses `/loom-skill-enhancement` as the current skill being enhanced; it does not change the generic mission of rewriting any skill being enhanced.
- The template authority is `assets/so-workflow/so-template.json`.
- The planning artifact is a temporary, runtime-owned file for one enhancement run and must stay at `<execution-output-root>/plan/skill-plan.md`. Never copy, move, migrate, or include its content in the skill being enhanced's assets, package, release, or deliverables. Runtime context and evidence may retain the path; a hash is optional generated metadata only and never a consumer validity, freshness, or revision gate. Do not require or publish a checked-in `assets/so-workflow/skill-plan.md`.
- The runtime lock is `assets/so-workflow/so-package-lock.json`.
- The current checked-in authority surface for this slice is `SKILL.md`, `assets/so-workflow/so-template.json`, `assets/so-workflow/contract.json`, `assets/so-workflow/governance-notes.md`, `assets/so-workflow/node-to-file-map.md`, `assets/so-workflow/so-package-lock.json`, `reference/execution-contract.md`, `reference/so-skill-reference.md`, `reference/review-and-evidence-contract.md`, `reference/plain-language-feedback.md`, and the affected workflow-designer authority documents; the per-run plan stays under the execution output root.
- The workflow first classifies governance state. If the target is already under Loom Skill Orchestrator governance, it inspects the current `SKILL.md`, package lock, and workflow assets, reuses the exact bound runtime version, captures a fresh guide, builds one bounded shared review context, and routes the three independent guide-delta reviews in an external `whenAllPass` group.
- After every re-enhancement gap result returns, one aggregator preserves all findings and dispositions before the explicit template-change strategy judgment. It records `local_patch`, `structural_refactor`, or `full_regeneration` as runtime-owned evidence before common plan analysis.
- `local_patch` is restricted to non-structural wording or metadata changes. `structural_refactor` requires an explicit old-to-new node and evidence mapping. `full_regeneration` is required when the old template conflicts with current requirements, concept documents, or the fresh guide, or when preserving the old shape would hide new behavior.
- For `structural_refactor` and `full_regeneration`, the old checked-in template is a baseline input alongside current requirements, concept documents, assets of the skill being enhanced, gap reviews, and the fresh guide. The workflow designer generates a new candidate template from that input set.
- The SO skill's self-bootstrap follows the same policy. It does not skip strategy judgment because the target is `/loom-skill-enhancement`, and it does not recursively launch another enhancement workflow.
- The common planning path is decomposed into scope input-output, route-gate, and evidence/node-map subagents running as one independent external `whenAllPass` group. A planning aggregator completes before workflow template drafting.
- Build the shared review context once after exact package integrity checks and fresh direct-apphost guide proof. Include checked-in snapshots, a source manifest, guide/schema/runtime references, and the same external workflow-copy identity. `context_hash` may be recorded only as optional generated metadata; consumers do not require, calculate, compare, re-attest, freshness-check, or gate on it.
- Independent external reviews consume that context by reference. All expected results must return before aggregation; missing or duplicate results fail closed.
- Every pass reads the exact package version from the skill lock, detects one host RID, reuses only a fully validated shared current-user OS-temp AO/SO generation matching exact package ID/version/RID and full `.nupkg` SHA-512, then checks the standard NuGet cache and acquires only that exact package on a miss. It runs `so.exe --guide`/`so --guide` as the first runtime operation. No resolver, descriptor, pre-guide MCP registration, or fragment inspection is required.
- The governed route now treats the selected guide surface and package-index references as explicit slice outputs rather than leaving them only in prose.
- SO compile and workflow-load validation enforce the governed workflow contract and business gates. Package readiness flows directly to fresh guide capture; there is no MCP-startup gate.
- The checked-in template remains the authority and runtime copies stay outside the skill. Direct edits to checked-in workflow JSON are not routine; only when the current direct SO apphost path is fully blocked and the user explicitly approves may an operator make the smallest workaround, then immediately return to the same published apphost `compile`, `run`, or `resume` path.
- The governed template now separates a compile-review prerequisite stage from the only full-delivery completion route after the shared entry gate.
- The compile-review prerequisite stage owns checked-in source deliverables, compile artifacts, confirmation, and review-fix evidence, but it is not a completion route.
- The `official runnable route` owns external runtime workflow copies, direct `so.exe run`/`resume` on Windows or `so run`/`resume` on Unix, runtime-owned evidence, and the completion manifest.
- The runtime-owned completion manifest is the fixed governance verdict surface for final handoff. It must summarize the verdict rule, current status and node, whether final `Done` was reached, any missing evidence, the next action, and explicit mappings back to the existing runtime-owned evidence families instead of introducing a parallel completion schema or a terminal self-certification step.
- The self-bootstrap pass still shows a user-confirmed review seam. After approval, the review-fix route runs a parallel pre-repair review batch, aggregates every finding, applies one coordinated repair, runs a parallel post-fix validation batch, aggregates those results, and performs final serial validation before the official runnable route can start. Agent-facing structured clarification uses `/loom-ask-user` by default, with or without a workflow; it is independent of the optional workflow `AskUser` node, and neither depends on the other. The workflow review seam remains unchanged and is not the default agent-facing question tool.
- The executable runtime path does not overwrite checked-in source assets; the runtime-owned completion step references checked-in deliverables instead, and should not be read as proof that it recreated those checked-in files.
- Compile-review and review-fix evidence are prerequisite checkpoints only and must not be described as completion.
- Official runtime completion means the public runtime chain reached final `Done`, and every blocked seam on that chain has a matching public `resume` on the same runtime workflow-copy lineage.
- In exclusive Loom Skill Orchestrator governance, SO is the only official execution authority. Ordinary workflow operations use the exact locked published SO product/RID apphost, not repository-source builds or manually assembled runtimes. Official run and resume use that same apphost and external workflow copy through final `Done`; compile alone is not completion.
- A bound runtime version change triggers a same-version differential semantic check, not only schema and compile checks. Use inherited and replacement variants of a minimal three-node fixture and require the replacement to reach final `Done` with the expected non-empty context value.
- The `0.3.282` probe forbids relying on literal `updates` under `noop` or `ToolCall` for context writes. Use `StateUpdate`/`MemoryWrite`; remove `$result` during upgrades unless the exact-version probe proves its result shape and projection.
- Shared obsolete patterns are migrated as one declared batch before per-target execution. Preserve idempotent migration-script hashes, dry-scan and target manifests, and post-migration results in `batch_migration_evidence`.
- Assumptions, corrections, decisions, probe records, `events.jsonl`, and audit references are durable per-run files under `<execution-output-root>/evidence/`; conversation-only decisions do not satisfy the workflow.

- Dependency acquisition follows the ordered L0-L6 policy in `reference/execution-contract.md`: L0 existing local artifacts/caches (validated shared SO cache before standard NuGet cache); L1 Agent/Host-controlled fetch for the exact NuGet package; L2 already-installed `nuget.exe` for the exact NuGet package only; L3 an already-installed runtime native in-process HTTP API, including a direct .NET `HttpClient` call from PowerShell; L4 an explicitly configured exact GitHub Release MCP asset; L5 another already-approved Host/MCP artifact source; L6 generic network CLI only after L0-L5 are exhausted and after one-operation user approval. PowerShell `Invoke-WebRequest`/`Invoke-RestMethod`, `curl`, `gh`, `wget`, BITS, and other shell/network download CLIs are L6; `nuget.exe` is the sole earlier CLI exception. After any failed request, do not automatically switch transports to repeat the same artifact/source. A nonblocked source may be retried only as an explicit L6 operation after L0-L5 are exhausted and the user approves that exact CLI action. If the source or request is explicitly blocked or denied by network/security policy, stop all attempts to that source through every transport; continue only with an independently configured and approved fallback source, otherwise stop and report the blocker. If the user denies CLI approval, stop and do not switch tools or sources to evade that decision. OS, endpoint, proxy, network, and EDR/SOC controls remain authoritative; these instructions cannot guarantee security alerts will stop. Preserve exact package ID/version/RID, package SHA-512 against exact registration metadata or matching same-version sidecar, safe archive/extraction, apphost, guide, and cache checks; keep L0-L6 out of the package lock.
- Verified audit reuse is an explicit supporting path through `copy-audit-step` or the paired run/resume reuse flags. It copies render artifacts with `audit-reuse.json` provenance and never replaces official workflow execution or evidence.
