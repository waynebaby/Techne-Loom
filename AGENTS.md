## Shared Python Environment

This workspace may use the shared virtual environment pointer from `.venv.path`.

- Resolve `.venv.path` with PowerShell on Windows or bash on Linux before invoking Python tooling.
- If the configured `.venv.path` target does not exist, initialize that virtual environment before invoking Python tooling.

## Run Output Naming

- When a skill creates a per-run output root, keep the skill-owned parent directory and name the run root `exec-<YYYYMMDD_HHMMSS>-<skill-slug>-result/`.
- Keep the timestamp immediately after `exec-` so runs remain sortable even when adjacent steps switch skills.

## Level 1 Rules

### Repository identity

- Techne Loom is a .NET-first multi-ecosystem mono-repo with parallel package families under `/src/dotnet`, `/src/nodejs`, and `/src/python`.
- Every source project remains buildable and testable. The active .NET NuGet release set contains the eight self-contained `Techne.Loom.Runtime.<rid>` packages and one no-RID `Techne.Loom.Abstractions` contract SDK, published at the same exact version and channel; the unified release line starts at `0.5.0-beta`.
- `AgentOrchestrator` and `SkillOrchestrator` are independent implementation modules under one public Loom CLI and runtime package series. They do not call each other and must not be framed as a parent/child runtime pair.
- Use `Loom Agent Plan-Execution Orchestrator` for AO user-facing narrative while preserving implementation identities such as `Techne.Loom.AgentOrchestrator`, `/loom-plan-execution`, and source/type names. The published executable is `loom`; public routes are `loom agent ...`, `loom skill ...`, and the single top-level `loom ask ...`.
- Use `/loom-ask-user` for agent-facing structured clarification with or without a workflow. It consumes the shared XO Ask capability through the single top-level `loom ask` route; the optional `AskUser` workflow node remains a separate consumer. The Loom runtime serves the browser form; the skill has no separate governance workflow or package lock and uses that exact runtime dependency.
- Use `enhancing skill` for `/loom-skill-enhancement` and `skill being enhanced` for the skill it creates or modifies; preserve exact `target_*`, `templateKind`, and workflow field literals in machine contracts.
- Workflow and process examples must include a complete Mermaid route with emoji, a nearby color legend, and readable labels; workflow JSON or `WorkflowInstance` examples must also include same-version direct-apphost `loom agent compile` or `loom skill compile` Mermaid evidence, while explanatory diagrams must be labeled as such.

### Subagent model requirements

- Subagents engaged in autonomous work must use GPT-6 Luna or Claude Haiku 5.5 as the minimum model standard. Do not silently fall back to a lower-tier model; if neither model is available for a required subagent, pause that delegated work and ask the user before proceeding.
- This model requirement applies only to subagents. It does not restrict the primary agent performing work directly in the current session.

### Safe editing and Git hygiene

- GitHub Copilot must not use `apply_patch` in this repository. Use the checked-in external-file-driven range editor or another repository-approved editing mechanism; do not embed multiline replacement content in commands.
- Preserve user changes. Do not use destructive Git commands or rewrite shared history unless the user explicitly requests it.
- For every commit whose changed paths and effects cannot influence any package publication, automatically include a standalone `[skip ci]` line in the commit message body before trailers; if package impact is uncertain, do not add it. This token skips all GitHub Actions, not only package-publishing jobs.
- For JSON larger than 16 KiB (16,384 UTF-8 bytes), default to selective reads: use search or regex only to locate a key/path, then inspect a bounded line window and expand as needed. For minified JSON or unsafe line slices, use JSON Pointer or a structured parser to extract the needed subtree. Read the full JSON only when explicitly requested or required for whole-document validation; `.agent.md` role contracts remain an independent full-read exception.
- AO and SO workflow-authoring prompts must produce C# builder scripts by default, not workflow JSON: use `Build(WorkflowScriptInput)` for new workflows and `Edit(WorkflowInstance, WorkflowScriptInput)` for revisions. `prompt-plan` and `prompt-replan` emit the corresponding complete script source without Markdown fences; direct model-authored JSON is not a fallback.
- For Agent and Skill workflow definitions and templates, use the same selected unified `loom` apphost through the owning `loom agent` or `loom skill` route and its disk-backed `--workflow-script` Roslyn path instead of a separate JSON-editing project: read the fresh top-level `loom --guide` and version-matched contract references. For a new workflow, run a `Build` script with `--mode build`. To revise an eligible draft, `--mode export` reads the external JSON and emits an `Edit` starter; edit that script, then use `--mode edit --base-workflow-file <draft-workflow.json>`. `prompt-replan` may also provide the Agent module `Edit` source directly. The same apphost reads/deserializes external JSON, executes the script, and compiles the resulting candidate. Scripts must not embed complete workflow JSON or perform file I/O; apphost-generated JSON remains canonical.
- Treat package `.csx.md` fenced code as reference text, never execute the Markdown fence directly, and do not directly edit workflow JSON as the normal authoring path or use this builder route to mutate a live `WorkflowInstance`. A direct JSON workaround requires an explicitly approved runtime blocker and must return immediately to the owning apphost compile/run/resume path.
- Every skill being enhanced that creates, edits, or maintains workflows must require C# `Build`/`Edit` scripts for new workflows and revisions, keep JSON external, and use the owning Agent or Skill route on the unified `loom` apphost for parsing, serialization, and compile; this applies to its own and future workflow modifications, not unrelated domain business prompts.
- File-valued CLI inputs are path-only and must be complete on disk before a command starts. Inline scripts, JSON, patches, workflows, references, or replacement content are not valid inputs.
- Keep generated output, audit material, caches, and temporary validation files outside source and skill directories unless they are explicitly requested deliverables.

- Keep directly invoked command lines at or below 200 characters, counting the full command passed to the shell.
- Save commands longer than 200 characters and substantial inline input to a run-scoped script/input under `.temp/`, `output/`, or OS temp; invoke scripts by path, not inline body.
- After failure, inspect state, error, and required inputs; fix the saved script/input before retrying. Never rerun unchanged content.

### Execution Continuity And Review Discipline

- Keep skill entrypoints at or below 200 lines; move detailed procedures into directly linked skill-local references with explicit stage-specific loading instructions. Preserve version markers, critical boundaries, and the complete contract.
- Use one request-level task ledger with stable task IDs and statuses `未开始` (not started), `进行中` (in progress), `受阻` (blocked), or `完成` (complete). Every item carries verifiable evidence, or an explicit no-evidence-yet statement, and its next action; completed items say no further action is required. Keep the task set and denominator fixed across phases. Report a progress percentage only against that fixed denominator and state the basis; otherwise show the checklist without a percentage. If scope changes, record and re-baseline the ledger explicitly rather than silently changing the denominator. Execution confidence is a separate estimate, not task completion.
- Before each run or resume, inspect the current persisted workflow copy and active wait (if any). For a wait, read its exact `transition_id`, applicable `wait_id`, `resumeOutputKey`, required fields and JSON/container types, nullability, ownership, context catalog, `outputPath`, and `outputBindings`; locally validate the complete payload before submission. Submit only missing caller-owned values and required new results; never replay runtime-owned context or copy instance-specific wait identifiers.
- After a failed run or resume, preserve runtime diagnostics and inspect saved events, persisted state, current wait, payload, and `caseId`/`runId` before acting. Do not retry an unchanged payload/action. If the runtime requires a fresh workflow lineage, retain static evidence only when its source snapshots, exact runtime/version, inputs, and dependencies still match; invalidate only affected evidence.
- Before a broad review or validation, inventory actual changed files and behavior boundaries, assess risk, and record the minimal checks with rationale. Reuse evidence supported by unchanged inputs, file snapshots, runtime/version, and dependencies; rerun only impacted checks and proven dependents. Default to one scoped review aggregation and one coordinated authorized repair pass; repeat only for a newly exposed defect, failed validation, or material risk change. Keep non-blocking recommendations distinct and preserve every required approval and terminal-state gate.
- Preflight the complete role contract before every reviewer/subagent call: exact non-empty frontmatter `name`, all required inputs and types, linked contract documents, and the declared output shape. A filename is never role identity. Resolve missing documents through the documented matching-skill-copy fallback; a driver may replace unavailable host registration, not missing contract content. When the name, inputs, or contract remain incomplete, preserve the diagnostic and block only dependent work; never guess a near-match role or silently skip a required review.
- For large workflows and review results, return an existing readable file path plus a bounded status/summary, needed JSON Pointer fragments, and evidence locations. Do not dump the complete workflow JSON into the conversation. Whole-document parsing or validation stays file-backed; full conversational output requires an explicit request and applicable size limits.
### Workflow invariants

- A workflow's business steps must match its declared business intent. Governed workflow instances declare `taskType` and `workflowKind`; enhancement and target-business workflows must not be interchanged.
- Plan, replan, compile, run, resume, and audit are disk-backed and sessionless. Each product owns one canonical `WorkflowInstance`; events, logs, audits, envelopes, and large artifacts are companion evidence, not a second mutable execution truth.
- `caseId` and `runId` stay on the same external workflow copy through the full execution chain. They identify one business execution and do not replace business outputs.
- AO and SO remain independent implementation modules with separate internal workflow capabilities, but share the `loom` CLI, runtime package, and release boundary.
- XO Ask is the workflow-independent shared ask capability exposed by the unified `loom` runtime; `XO` is shorthand for AO or SO implementation modules, not a third product. `/loom-ask-user` and the `AskUser` workflow node are peer consumers and neither depends on the other.
- The shared Common XO Ask service owns ask-scoped questions, validation, drafts, answers, and receipts only. Standalone sessions do not require or mutate a `WorkflowInstance`; for the optional node adapter, the owning AO/SO path validates the receipt, maps answers, and performs its existing resume. Workers never lock or mutate a workflow and never resume it.
- `requiredInputs` and SO `validation.declaredUserOwnedFields` apply only to the workflow-node adapter; standalone question contracts have no workflow context-path requirement.
- Every skill-owned contract defines the versioned `context_fields` catalog as the sole authority for business context paths, JSON types, nullability, and container item/value types; workflow definitions and resume descriptions consume derived views instead of duplicating this catalog.
- Workflow definitions, task models, serialization contracts, and their wire constants are owned by `Techne.Loom.Abstractions`; AO/SO/Common contain runtime implementations and derived views, not duplicate workflow contract models.
- AO/SO compile and run/resume validate the current owning catalog. For statically identifiable expression reads such as `context.Get<T>("path")`, compile verifies that the consumer type matches the catalog type; incompatible or conflicting consumers fail with actionable diagnostics. `Has(path)` checks presence only and does not establish a type. No implicit string-to-boolean/number conversion may hide a mismatch.
- External `resumeOutputKey`, `outputPath`, and `outputBindings` destinations must agree with the same catalog. Runtime validates actual payload/context values before mutation, preserves missing/null/false distinctions, and rejects writes to runtime-owned fields.
- Every weave-out includes catalog-backed payload type metadata, selectable typed suggestions or an explicit empty-with-reason result, bounded current/direct-successor consumer expressions, and optional host guidance for a decision model/tool/skill/MCP. Suggestions and type validity never prove evidence or replace human approval; Loom never invokes model APIs.
- Claim the workflow-free `ask` route only for a published `loom` apphost whose fresh help exposes the single top-level `ask start` and `ask result` commands.
- Governed routes use bounded workflow-fragment access when a workflow step needs it, but runtime bootstrap proceeds from self-contained package extraction directly to fresh `--guide` without resolver descriptors or a required MCP/fragment startup gate.
- AO/SO skills share verified runtime packages in a current-user OS-temp cache. Each immutable generation is identified by product/package ID, exact version, RID, and full `.nupkg` SHA-512; short hash prefixes only abbreviate the path. For NuGet-sourced packages, verify downloaded bytes only against the exact version registration `catalogEntry.packageHash`; do not require a separate NuGet `.nupkg.sha512` sidecar. For GitHub fallbacks, use the exact `.nupkg.sha512` link in the selected package index and verify it against the GitHub package bytes. Keep checksum authorities source-specific. Stage and validate repairs before atomic publication, preserve generations used by active apphosts, and retain valid entries for the OS-temp lifecycle.
- Every skill that acquires an external runtime, dependency, or artifact follows the Dependency Acquisition Fallback Policy in `.github/instructions/loom-runtime.instructions.md`. Generic network CLIs, including first-party PowerShell web commands such as `Invoke-WebRequest`/`Invoke-RestMethod`, `curl`, `gh`, `wget`, and BITS tools, require explicit per-operation user approval. Classify by transfer mechanism: a direct in-process .NET `HttpClient` call from PowerShell is L3; PowerShell web cmdlets remain L6. After any failed request, do not automatically switch transports to repeat the same artifact/source. A nonblocked source may be retried only as an explicit L6 operation after L0-L5 are exhausted and the user approves that exact CLI action. A blocked or denied source cannot be accessed through another transport. Never install a runtime or downloader solely for acquisition. This guidance does not override OS security controls or guarantee that alerts stop.
- Exact NuGet acquisition completion rule: for `/loom-ask-user`, `/loom-plan-execution`, `/loom-skill-enhancement`, and every skill created or updated by `/loom-skill-enhancement`, downloading a missing exact-version NuGet package is allowed and required. A local miss is never a terminal outcome: do not end, skip, mark complete, or substitute another version, RID, channel, local/test build, or agent-native fallback because the package is absent. When L0-L2 do not yield the verified package, write a short single-purpose download program file outside source and skill folders that uses an already-installed runtime's in-process HTTP API (.NET `HttpClient` hosted by PowerShell or `dotnet`, Python `urllib.request`, or Node `fetch`) and run it; while such a runtime exists, do not call `curl`, `wget`, `gh`, BITS, `Invoke-WebRequest`, `Invoke-RestMethod`, or another shell/CLI fetch, not even as an approved L6 retry. Retry a nonblocked source by re-running the same runtime program, and use an approved L6 CLI only when no installed runtime offers an in-process HTTP API. The run must not complete, skip, terminate, or record a terminal failure until the exact package is downloaded and verified. A policy block or denial, a denied L6 approval, an exact version not yet published on any approved source, or repeated integrity mismatches are never bypassed: stop only that source or tool, keep the run in a resumable acquisition-pending pause with state and evidence, ask the user for an approved source, credentials, policy change, or publication wait, then resume acquiring the same exact version. For these packages, every generic acquisition "stop" outcome means this pause, never completion, success, or a terminal outcome.
- AO/SO artifact delivery covers Mermaid, HTML, Analysis, and Dataflow when generated. Return the complete local file URL for each artifact in the standard three-slash `file:///` form, which is `file://` plus an empty authority plus the absolute path: `file:///C:/...` on Windows and `file:///...` on Linux/macOS. Drive-letter case is insignificant. Never emit the two-slash `file://C:/...` form, which places the drive letter in the URL authority and does not open. Verify that the URL resolves to an existing readable file in the active host. If it does not, create and verify a mirror in the current workspace and use the mirror's full file URL. Encode every space in the URL as `%20`, and use the identical encoded URL in its clickable Markdown link and text fence. Never emit a literal space in the URL, a bare path, or a code fence as a substitute for a link. Never truncate or guess an address; if no file URL resolves, report a delivery blocker. If it does not, create and verify a mirror in the current workspace and use the mirror's full file URL. Encode every space in the URL as `%20`, and use the identical encoded URL in its clickable Markdown link and text fence. Never emit a literal space in the URL, a bare path, or a code fence as a substitute for a link. Never truncate or guess an address; if no file URL resolves, report a delivery blocker.
- Progress reports for `/loom-skill-enhancement`, `/loom-plan-execution`, skills created or updated by `/loom-skill-enhancement`, and `/loom-ask-user` when it emits a report must use the platform helper bundled with the reporting skill under its own `assets/scripts/AppendProgressReport.ps1` or `assets/scripts/AppendProgressReport.sh`. Resolve the active skill root and invoke only that skill-bundled helper; never use a repository-global helper or another skill copy. Prepare the complete Markdown entry in a separate file with ISO 8601 UTC and local timestamps including numeric UTC offset and OS timezone ID. The helper reads only that entry file and append-writes the target, then prints its full file URL; use that exact URL if reporting the target. Never read, open, or inspect the existing `progress-report.md`, and never use read-modify-write or a manual fallback. If a helper fails, preserve prior entries, report the failure, and pause later business-step progression without changing workflow execution state.
- Workflow designers use version-matched English technical documentation as authority; translated public documentation does not substitute for the English runtime docs.
- Prefer fan-out only when branches are logically independent, the host can dispatch them concurrently, and each branch writes to an isolated output path; keep dependent or shared-write work sequential.
- Keep transition/group pass results distinct from workflow terminal status. `firstPass`, `whenAnyResponse`, and `whenAnyPass` route to the selected transition target; aggregation strategies require an explicit join target, while no-pass and execution-error routes remain distinct.
- If the host cannot dispatch concurrently, execute branches sequentially without changing the selected strategy semantics. Request cancellation when a strategy finishes early, persist logical cancellation when physical cancellation is unavailable, and reject late results.

### Default Autonomous Execution And Bounded Recovery

- When a user requests an end-to-end outcome and has not limited the request to planning or analysis, proceed through implementation and required validation without pausing for routine technical choices. Derive versions, paths, and repository facts from checked-in contracts, package locks, fresh guides, and verified state rather than asking the user to restate them.
- Batch known independent user-owned decisions into one structured clarification. Pause only for genuinely missing business input, required human approval, explicit security or policy blocks, or external/irreversible actions outside the user's authorization. Never fabricate approval; continue independent safe work.
- Before accepting generated candidates, verify portable paths, exact version/channel consistency, the intended changed-file set, stale active references, unintended deletions, and required compile/runtime completion evidence.
- Diagnose failures from preserved evidence and never repeat an unchanged operation. Consolidate known findings into one evidence-backed repair round; start another only for a newly evidenced issue, rerun only checks affected by changed inputs, and still complete every repository-mandated validation and release gate. Do not add effectiveness benchmarks or exploratory test loops unless requested.

### Phase-sliced workflow design

- Enable phase slicing at 40 or more authored state nodes; use 25 as a soft cap per phase. Count authored state nodes only, excluding transitions and synthetic harness nodes. Existing oversized workflows receive warnings, not automatic rejection.
- Freeze stable phase IDs and typed ports before phase authoring. The owning versioned `context_fields` catalog remains the sole type and ownership authority; each shared business field has one producing phase, and cross-phase routes and backedges are declared.
- Phase-local compilation is static only. Synthetic harness inputs and nodes cannot perform business side effects or satisfy business gates. Merge creates a new candidate and must pass the complete owning AO or SO compile.
- Common owns shared design contracts and checks; AO and SO remain independent modules with distinct command semantics and compilers under the unified `loom` CLI and runtime package family. Rework follows the declared impact closure. No live `WorkflowInstance`, history, or pending-result migration is in scope.

### Synthetic Scenario Validation

- For skill authoring, enhancement, or validation, treat each synthetic case as an independent scenario with its own inputs, expected outcome, pass condition, observed evidence, and verdict; label synthetic evidence and never substitute it for real business validation, human approval, or live external-system results.
- Before execution, confirm dependencies, state/artifact isolation, and resource/concurrency capacity. Independent scenarios meeting those conditions must run in parallel; assign workers to available capacity, not one per scenario. Batch or serialize dependent, shared-state, non-isolated, or over-capacity cases. Parallelism does not guarantee speedup or reduce per-scenario coverage and evidence.
- Aggregate only after every expected scenario result arrives, make one coordinated repair pass, and rerun only checks affected by changed inputs/files.
- For bounded skill-enhancement requests, default to autonomous execution through planning, candidate work, repair, review, and required validation without asking for inferable facts or ordinary technical choices. Pause for genuinely user-owned decisions/approvals, unauthorized consequential external/irreversible actions, or safety/policy blocks; never fabricate approval or repeat an unchanged failure. Preserve independent safe progress.
- Before completion, reconcile target files, portable paths/version, candidate-to-source writeback, old active references, unexpected deletions, and compile/run status; distinguish candidate generation, compile success, source update, and required end-to-end completion. See [shared skill-governance rules](./.github/instructions/loom-skill-governance.instructions.md).

### Documentation and public contracts

- Public documentation is bilingual by default under mirrored `/docs/en` and `/docs/zh-cn` trees. Root public docs require their Chinese mirrors; `AGENTS.md` and other agent configuration files remain English-only.
- Workflow definition files are the canonical English carrier for schema keys and control semantics. Localization belongs in the presentation layer and must not change wire names or workflow behavior.
- State node names pair checkpoint identifiers with concise business wording; descriptions state the business purpose, and workflow phases include a stable stage identifier plus a readable phase name.
- Successful compile Mermaid output is derived from the workflow. Compile audit HTML may summarize only recorded feedback, analysis, and dataflow evidence; failed compile must not emit placeholder renders.
- Keep `AGENTS.md` at the repository root. Do not create a second agent-rules source under `docs`.

### Branch and package channel locks

- Classify each activity by purpose, not branch name or output file type: authoring, debugging, or improving a skill/workflow is development; invoking a skill to produce requested domain code, projects, or documents is business execution.
- Development may use a compatible current-source or candidate self-contained `loom` apphost without an exact published lock or a full candidate run/resume chain for every phase iteration. Prepare runtime references once per development run, record the module, version, RID, and provenance, and label evidence development-only. Never refresh a checked-in lock from an unpublished candidate.
- Development support references, shared context, schema/demo descriptors, skeletons, phase candidates, plans, scripts, and support reports do not require hashes, re-attestation, or substitute revision/fingerprint gates. They must still be readable and pass actual schema, type, interface, ownership, path, security, and compile checks. If a published package is used, package identity, SHA-512, and safe-archive checks remain mandatory.
- Target business outputs exercised during development remain production-validation objects. Compute and verify every hash required by the target business contract against the actual artifact using its declared algorithm and canonicalization. Missing, invalid, or mismatched required hashes block acceptance, delivery, and production-ready claims; preserve the failure and require fresh passing validation after repair.
- Development allowances do not waive formal check-in, CI, package, or release gates. Official channel execution and publication use published exact versions and locks. Source check-in still requires `loom agent` and `loom skill` schema/demo exports from the same self-contained RID apphost into separate external directories, same-apphost demo compiles, focused tests, and platform gates; current-source evidence must be labeled development-only.

- For checked-in release surfaces, treat `main` as the release branch: resolve the latest published stable (`release`) NuGet version and use that exact version for release-channel runtime locks, package references, guide metadata, and provenance surfaces.
- For checked-in beta surfaces, treat `development` as the beta branch: resolve the latest published prerelease (`beta`) NuGet version and use that exact version for beta-channel runtime locks, package references, guide metadata, and provenance surfaces.
- When refreshing a checked-in lock, select the channel from the current branch and use only a version actually published on NuGet. Keep the complete eight-package `Techne.Loom.Runtime.<rid>` closure plus the no-RID Abstractions SDK (nine packages total) and matching runtime locks on one compatible exact version; never mix `release` and `beta`, copy a version from the other branch, or use a floating `latest` alias.
- This lock-refresh rule is separate from release version calculation: `release-set.json` and the shared version job may select the next monotonic version after the published high-water mark for a new release. Do not write that unpublished candidate into an existing runtime lock until it is published.
- When a workflow-template migration introduces fields or enum values newer than its current locked runtime, compile with both the exact locked apphost and the candidate apphost. Record a locked-runtime failure as a version-compatibility finding; candidate success does not prove the current lock is compatible. Never put an unpublished candidate in a checked-in lock. If a push is intentionally used to trigger publication, verify the exact package and version after CI/CD succeeds, then refresh the lock to that published version before treating the template as officially usable.

### Validation and delivery

- For package-impacting source, test, workflow, package, or build-input changes on `development` and `main`, start Windows and WSL restore, build, and test jobs in parallel. Keep their build/intermediate outputs isolated, collect results separately, and wait for both before declaring validation complete. Commits intentionally marked `[skip ci]` because they cannot affect package publication follow the review-only exception under Development-to-main promotion.
- Pure article-publication pushes that touch only `docs/en/articles/**`, `docs/zh-cn/articles/**`, `docs/assets/images/**`, or `docs/assets/attachments/**` are documentation-only: the package-publishing workflows must skip restore/build/test, schema-demo generation, and package publication for them. Keep matching `paths-ignore` filters in both `publish-development.yml` and `publish-main.yml`; retain `workflow_dispatch` as an explicit full validation/release route. Any push that also changes a path outside these exclusions follows the normal workflow.
- Tests that exercise intentionally long-running tasks must not set a test timeout or add timeout-based cancellation merely to shorten the run. Let the task complete naturally and distinguish genuine failures from runner or environment interruption.
- Before source check-in for package-impacting changes, generate AO and SO schema/demo files through their `loom agent` and `loom skill` routes on the same self-contained RID apphost, in separate external directories, then compile each demo with that apphost. Development may use a compatible current-source or candidate apphost and must label its provenance and evidence development-only; official package execution/publication uses the published channel version. Run focused tests and platform validation for the affected scope. Intentional `[skip ci]` commits are exempt from these build/test and schema/demo requirements. Detailed commands and artifact rules are in the validation instruction document.
- Review every major implementation slice. Run validation required by its package-impact classification before starting the next slice; intentional `[skip ci]` commits follow the review-only exception under Development-to-main promotion. Do not carry unreviewed or uncommitted major work across slices unless the user explicitly overrides the cadence.

### Development-to-main promotion

- Use `development` as the integration lane. Validate and push the exact source baseline intended for promotion to `origin/development`; branch-locked beta/release package versions remain governed by the branch-channel rules above.
- Author all requested code, documentation, and CI/CD fixes on `development` first, including fixes for `main` CI/CD. Never use `main` as a normal editing branch. During promotion, edit `main` only to resolve merge conflicts. If a main-only CI/CD repair cannot be fixed on `development`, stop for explicit user approval; after an approved repair, immediately port it to `development` so the branches do not drift.
- For package-impacting commits, omit `[skip ci]`, complete the required Windows/WSL validation, and wait for the GitHub Actions run associated with the exact pushed development commit to succeed. If it fails, debug and fix on `development`, repeat validation, push the fix, and wait for that commit's run to succeed.
- For commits intentionally carrying `[skip ci]` because they cannot affect package publication, do not run local builds/tests or wait for Actions; complete review and basic Git checks, and treat the absence of an Actions run as intentional. Apply this rule to any main merge commit as well.
- After the applicable development gate passes, treat promotion to `main` as an explicit checkpoint. If the user does not request or approve main promotion, stop without merging or pushing `main`.
- When promotion is approved, fetch the latest `origin/main`, update local `main` safely, and merge local `development` into local `main`. Confirm the merge result. For package-impacting changes, validate the merged baseline on isolated Windows and WSL lanes; for intentional `[skip ci]` changes, perform review and basic Git checks only.
- Push `origin/main`. For package-impacting changes, verify the pushed commit's Actions run succeeds; on failure, debug through `development` and repeat validation and promotion. For intentional `[skip ci]` changes, verify the exact pushed commit and complete without waiting for Actions. Never treat a failing or pending required run as success.
